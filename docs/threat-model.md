# Production threat model

## Reviewed contenteditable single-select boundary

Reviewed Greenhouse Contenteditable Single-Select `v0.81.0-alpha.1` grants no generic content-editing authority. A custom Greenhouse control is eligible only when it is an input or a live contenteditable `div`/`span` and the existing single-select contract proves an exact expanded combobox, one controlled visible listbox, no multiselect, one semantic locator, unique nonempty enabled option labels, and no unsafe visibility, state, repeated, conditional, legal or signature semantics. The worker records editability from `element.isContentEditable`, uses exact role/name location for ARIA-labelledby custom comboboxes, and reproves live editability and listbox ownership before one scoped exact-label option click. Verification reads normalized text only from a still-contenteditable element. Changed state, ambiguous controls and uncertain outcomes fail closed; no automatic retry or widget-opening behavior is added.

## Reviewed direct-link navigation boundary

Reviewed Browser Link Navigation `v0.80.0-alpha.1` grants no generic link-click authority. The backend may expose only one uniquely keyed, visible, enabled, non-busy, non-inert, accessibility-visible native anchor on the current supervised non-Greenhouse page. Query values, fragment values, embedded usernames and passwords are stripped from observations and represented only by presence flags; any such link, download, non-HTTP(S) target, already-current target, foreign origin, cross-portal host or duplicate is ineligible. The review fingerprint binds the exact policy, run/session/portal boundary, source evidence, control label and normalized target. Renderer input cannot supply or alter the URL. Electron confirmation defaults to Cancel. Approval reobserves after resume, reproves the review and dispatches one direct exact-URL navigation instead of invoking provider-controlled click handlers. Redirects, stale evidence and uncertain responses fail closed; automatic retry is prohibited.

## Exact URL navigation reconciliation boundary

Reviewed Browser Exact URL Reconciliation `v0.79.0-alpha.1` grants no generic link-click or redirect authority. An exact direct URL action receives encrypted intent before dispatch only when it is a standard `NAVIGATE`, the HTTP(S) target is allowlisted and differs from the current URL, exact `URL_EQUALS` is its postcondition, and it carries no locator, coordinate, value, file, precondition, elevation, or confirmation. Preview and approval each require the exact target URL/origin, a changed page fingerprint, a bounded page type, and worker-maintained `previous_action = NAVIGATE`. The full source/target URLs remain inside authenticated encrypted intent and keyed evidence; the public preview exposes only scope, page types and fingerprints. Partial URLs, redirects, already-current targets, arbitrary clicks, manual browsing, missing provenance, mixed restore payloads and stale reviews fail closed. Reconciliation performs no browser mutation, leaves the original effect `UNCERTAIN`, and retains takeover.

## Reviewed upload reconciliation boundary

Reviewed Browser Upload Reconciliation `v0.77.0-alpha.1` grants no generic upload retry or success assertion. Authority exists only when encrypted intent was prepared before dispatch for the exact reviewed Greenhouse file control. It binds operation/attempt/request, locator/control, source origin/page/stage/form review/upload status, and exact filename/byte count/SHA-256. Persisted actions redact paths and staged plaintext is cleared after the attempt. Preview and approval each use fresh read-only observation and require the same origin, page type and stage, a changed fingerprint, and exactly one expected filename. The renderer cannot choose the file, path, hash, evidence or outcome. Path-like names, unsupported suffixes, absent/duplicate/stale names, another stage/origin, changed reviews and old/generic uploads fail closed. Recorded filename evidence does not establish provider receipt, content, retention, parsing, attachment or submission.

## Reviewed navigation reconciliation boundary

Reviewed Browser Navigation Reconciliation `v0.76.0-alpha.1` does not infer success from a changed URL or page alone. Reconciliation authority must exist before dispatch and is limited to the exact reviewed Greenhouse navigation contract. Encrypted intent binds operation, attempt, request, control, semantic locator, source origin/page/stage, form-review fingerprint, and source page fingerprint. Both preview and approval independently perform a read-only observation and require the same origin plus a different, recognized, strictly later non-confirmation stage. Renderer input cannot choose the evidence or target stage. The original effect remains immutable and `UNCERTAIN`; reconciliation never replays a click and never grants upload or submit authority. Same-page, earlier/equal, confirmation, unknown, foreign-origin, stale, generic-click, and changed-review cases fail closed.

## Protected assets

Candidate identity and history, resumes, answers, browser sessions, mail/calendar data, application evidence, encryption keys, API/provider credentials, backups, and release artifacts require protection. Availability of local recovery data and integrity of submission evidence are as important as confidentiality.

## Abuse cases and response

- A malicious page instructs the agent to ignore policy: treat page text as data; only deterministic application policy authorizes actions.
- A stopped persistent profile is requested under a differently cased name or another tenant/origin set: reject before allocating a session or calling the worker and require a new profile name. Never infer login status or store the account password.
- A renderer requests profile retirement with a path, stale metadata, an active profile, or changed/reparse-backed storage: ignore renderer authority, derive the canonical path, fail before deletion, and require a fresh cancel-default native review. Preserve session evidence and block historical-name reuse after successful isolation.
- A click occurs without reliable confirmation: record attempted/uncertain, never confirmed, and require review.
- A direct navigation response is lost and the browser is redirected, manually moved, unchanged, or lacks exact worker provenance: keep the effect consumed and unresolved; never infer the target from a substring or replay the navigation.
- A backup is changed or contains traversal paths: fail verification before staging and preserve the current installation.
- A restored database contains unknown/altered tables, indexes, uniqueness, foreign keys, triggers, views or virtual schema, or it loses/changes recorded dependency/attempt history: reject before operation allocation and live writes. Do not query the staged SQLite file until its complete reviewed source bytes are authenticated. Inspect only compiled schema-0028 definitions under bounded query-only settings; authenticate encrypted fields and document hashes; require exact calendar claim → audit → plan relationships, relational/ownership closure, unchanged current rows and exact mutable authority/session/cache sets.
- A renderer or stale review tries to create a calendar event for a changed account, credential epoch, scope, adapter or plan: reject before claim/token access and require a freshly fetched native review. Main, not the renderer, owns actor and attempt identity; cancel remains the default.
- A calendar create times out, disconnects, returns a malformed/oversize/compressed response, loses its terminal database write, or restarts with a `PLANNED` claim: keep the one attempt consumed and require reconciliation. Never turn provider-native duplicate keys into automatic retry authority. `CONFIRMED` means only a validated provider acceptance identifier, not invitation delivery or readback.
- Candidate bookkeeping attempts a trigger/recursive source, delete, function, pragma, attach, schema change, unrelated-table mutation or future unknown SQLite action: deny by default. Permit only direct reads/transactions and required inserts/named-column updates in the exact `backup_manifests` and `restore_plans` physical schemas. Recheck mail history and then the complete serialized history against the retained original byte snapshot without a plaintext scratch database; immediately before activation, recheck every live target against its sealed `BEFORE` state.
- Restore preparation fails after allocating evidence but before guard activation: under the exclusive lease, remove only the exact new operation after strictly inventorying it. If links, unexpected files or cleanup failure make that proof impossible, preserve the residue and count it against future quota admission rather than recursively deleting evidence.
- A restore crashes after guard activation: normal packaged startup, migrations, API, renderer and updates remain blocked. Load only the existing OS-protected key and offer native authenticated exact rollback or terminal finalization with cancellation as the default; legacy, corrupt, changed or ambiguous evidence remains blocked.
- A recovery helper hangs, emits stderr, oversized/unexpected JSON or a mismatched terminal result: terminate the recovery-only session without normal startup and never infer success from process launch or dialog confirmation alone. Before any authorized mutation the guard remains; afterward, preserve evidence and reauthenticate on-disk terminal/guard state because the backend command may already have completed safely before observation failed.
- The database is locked or migration fails: mark runtime degraded, do not start automation, preserve database and diagnostic evidence.
- An update is unsigned or signed by another publisher: reject installation and retain the current version.
- A diagnostic error contains a token value: export only the context key name; values never cross the diagnostics contract.
- The backend or browser process exits: surface degraded state, retain checkpoints, and require an explicit retry or restart.

## Residual risk and launch constraints

Reviewed Profile Quarantine Recovery `v0.75.0-alpha.1` retries removal only for one profile-associated quarantine whose exact stopped history, absent canonical directory, opaque UUID, ordinary root, and bounded inventory are freshly reviewed. Duplicate, case-aliased, unsafe, restored-canonical, stale, or malformed targets fail closed. A matching directory name is not cryptographic proof against a hostile local administrator; administrator/kernel tampering remains outside the application trust boundary. Anonymous v0.74 quarantines remain manual-support cases. This is not provider logout/revocation, forensic secure erasure, automatic retention, or bulk cleanup. Exact source checkpoint `18cc87691558bfe0509a5c0d48e1791b7ba99783` and unsigned package checkpoint `783c6662071b5a8001d3e27f6b491362aaabb19b` pass their local gates; physical failure-injection evidence remains pending.

Reviewed Portal Profile Retirement `v0.74.0-alpha.1` remains the underlying removal boundary. It removes only one stopped local browser profile after an authenticated inventory and native review, atomically isolating it before cleanup while retaining history and blocking name reuse. Exact local source and unsigned package gates pass.

Origin-Bound Portal Profiles `v0.73.0-alpha.1` prevents one engine/profile directory from being silently reused across differently cased Windows aliases or exact origin sets. The binding is historical and fail-closed, and the UI exposes only local profile metadata. Browser-managed cookies remain sensitive local data outside the database contract; this build does not inspect them, prove account authentication, provide profile deletion/retirement, validate a live portal, or prevent a user from signing into multiple accounts manually on the same allowed origin. Use a distinct name per tenant/account and protect the Windows user profile.

Reviewed Browser Field Reconciliation `v0.71.0-alpha.1` narrows one consumed browser ambiguity without granting retry authority. Only eligible reviewed field actions receive a pre-dispatch encrypted intent containing the exact deterministic postcondition. Reconciliation requires the same durable operation and latest attempt, `UNCERTAIN` status, `USER_TAKEOVER`, original page fingerprint and origin, two matching read-only worker proofs, a current keyed review fingerprint, and cancel-default native approval. The renderer never receives the expected value and cannot provide an action, locator, verification, URL, evidence result, or success status. The original uncertain record remains immutable. Replay, stale preview, page movement, unsupported action, missing intent, malformed encrypted data, verification mismatch, observation failure, and evidence-persistence failure all leave the effect unresolved. A compromised provider page may still display deceptive content; this contract proves only the exact DOM field postcondition on the unchanged locally observed page, not provider delivery or downstream acceptance.

Reviewed Greenhouse Single-Select Widgets `v0.70.0-alpha.1` grants custom-field authority only when a fresh Greenhouse assessment proves one visible enabled input combobox is already expanded, controls exactly one visible non-multiselect listbox, has one semantic locator and exposes non-empty case-insensitively unique labels. The renderer may derive `SINGLE_SELECT_WIDGET` only from that current `REVIEW_FIELD` contract and cannot manually select that kind. The backend rechecks the reviewed answer, binding, page and form fingerprints before decryption. The worker then rechecks live role, tag, popup, expansion, visibility, enabled state, ownership and option uniqueness, and scopes the exact label lookup to the one controlled listbox. It refuses a collapsed or changed widget rather than opening it. Internal option values, page-wide option search, other portals, multiselects, duplicate labels, legal/signature fields, repeated controls and generic custom widgets grant no authority. Sensitive values remain redacted; an ambiguous dispatch is consumed, requires takeover and cannot retry automatically.

The v0.69 final-submit boundary remains separate: a compromised renderer can supply only run, page-review and form-review identities; strict request parsing rejects extra URL, locator, action, portal or control claims. Both global execution flags, the Greenhouse allowlist, a fresh allowed-origin page, exact current page/form reviews, stage `REVIEW` and one safe `FINAL_SUBMISSION_GATE` remain required. Only a recognized same-origin confirmation page with an identifier can produce `SUBMISSION_CONFIRMED`; any ambiguity becomes `SUBMISSION_UNCERTAIN`. No field, upload, navigation, manual-handoff or final-submit authority is inherited between captures. Live Greenhouse behavior is unproven and production flags remain off.

Durable External-Effect Ledger `v0.63.0-alpha.1` closes the unjournaled pre-dispatch window for browser actions and AI completion/embedding provider calls. Response loss, unknown exceptions, local-evidence persistence failure and interrupted dispatch are consumed `UNCERTAIN` outcomes: AI fallback stops and browser automation requires user takeover. The ledger cannot prove remote state and does not authorize calendar UPDATE, unattended scheduling, portal submission or live-provider claims. Mail, calendar CREATE and Gemini cleanup retain their specialized journals. Source tests cannot establish actual provider retention, delivery, account-policy compliance or physical desktop behavior; every consumed uncertain attempt requires provider/browser reconciliation before a deliberately new action.

Durable Restore Rollback `v0.61.0-alpha.1` passed its full local source gate, exact backend-dist/delivered-package smokes, delivered supervisor lifecycle, source-controller-to-delivered-backend recovery protocol, protected pull-request integration and post-merge main checks. Schema `20260915_0030` source requalification covers 47 protected tables with v0.71; physical installed Windows recovery evidence remains separate. Path and lease checks are cooperative rather than handle-pinned isolation from a malicious local process; sequential writes are not a multi-file transaction or arbitrary power-loss guarantee. V2 forward admission preserves the explicitly compiled recorded-history graph, while rollback returns only the guarded operation's exact sealed targets. Neither can merge later history, automatically choose recovery, resume forward apply or prove remote state for an ambiguous effect. The delivered protocol gate mocks Electron key decryption and dialogs, so it does not establish real installed `safeStorage`, native-dialog, entry-point restart or power-loss behavior.

Alpha builds do not authorize live generic-portal submission. Production enablement requires named integration owners, current terms/legal review, authorized test accounts, real Windows desktop validation, portal replay plus supervised live validation, a protected signing certificate, incident-response ownership, and a rollback drill using the exact candidate installer. CAPTCHA solving and legal attestations are permanently human-only boundaries.
