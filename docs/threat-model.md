# Production threat model

## Protected assets

Candidate identity and history, resumes, answers, browser sessions, mail/calendar data, application evidence, encryption keys, API/provider credentials, backups, and release artifacts require protection. Availability of local recovery data and integrity of submission evidence are as important as confidentiality.

## Abuse cases and response

- A malicious page instructs the agent to ignore policy: treat page text as data; only deterministic application policy authorizes actions.
- A click occurs without reliable confirmation: record attempted/uncertain, never confirmed, and require review.
- A backup is changed or contains traversal paths: fail verification before staging and preserve the current installation.
- A restored database contains unknown/altered tables, indexes, uniqueness, foreign keys, triggers, views or virtual schema, or it loses/changes recorded dependency/attempt history: reject before operation allocation and live writes. Do not query the staged SQLite file until its complete reviewed source bytes are authenticated. Inspect only compiled schema-0028 definitions under bounded query-only settings; authenticate encrypted fields and document hashes; require exact calendar claim → audit → plan relationships, relational/ownership closure, unchanged current rows and exact mutable authority/session/cache sets.
- A renderer or stale review tries to create a calendar event for a changed account, credential epoch, scope, adapter or plan: reject before claim/token access and require a freshly fetched native review. Main, not the renderer, owns actor and attempt identity; cancel remains the default.
- A calendar create times out, disconnects, returns a malformed/oversize/compressed response, loses its terminal database write, or restarts with a `PLANNED` claim: keep the one attempt consumed and require reconciliation. Never turn provider-native duplicate keys into automatic retry authority. `CONFIRMED` means only a validated provider acceptance identifier, not invitation delivery or readback.
- Candidate bookkeeping attempts a trigger/recursive source, delete, function, pragma, attach, schema change, unrelated-table mutation or future unknown SQLite action: deny by default. Permit only direct reads/transactions and required inserts/named-column updates in the exact `backup_manifests` and `restore_plans` physical schemas. Recheck mail history and then the complete serialized history against the retained original byte snapshot without a plaintext scratch database; immediately before activation, recheck every live target against its sealed `BEFORE` state.
- Restore preparation fails after allocating evidence but before guard activation: under the exclusive lease, remove only the exact new operation after strictly inventorying it. If links, unexpected files or cleanup failure make that proof impossible, preserve the residue and count it against future quota admission rather than recursively deleting evidence.
- A restore crashes after guard activation: normal packaged startup, migrations, API, renderer and updates remain blocked. Load only the existing OS-protected key and offer native authenticated exact rollback or terminal finalization with cancellation as the default; legacy, corrupt, changed or ambiguous evidence remains blocked.
- A recovery helper hangs, emits stderr, oversized/unexpected JSON or a mismatched terminal result: terminate the recovery-only session without normal startup and never infer success from process launch or dialog confirmation alone. Before any authorized mutation the guard remains; afterward, preserve evidence and reauthenticate on-disk terminal/guard state because the backend command may already have completed safely before observation failed.
- The database is locked or migration fails: mark runtime degraded, do not start automation, preserve database and diagnostic evidence.
- An update is unsigned or signed by another publisher: reject installation and retain the current version.
- A diagnostic error contains a token value: export only the context key name; values never cross the diagnostics contract.
- The backend or browser process exits: surface degraded state, retain checkpoints, and require an explicit retry or restart.

## Residual risk and launch constraints

Greenhouse Form Execution Contracts `v0.66.0-alpha.1` preserves the v0.65 reviewed launch and adds a Greenhouse-only current-page assessment. It accepts only HTTPS `greenhouse.io` origins and recognized stages, binds required control metadata and unique navigation to the page fingerprint, refuses unsafe/repeated/custom/legal controls, and defines exact upload and later-stage postconditions. Upload proof requires the admitted staged basename to be new and observed exactly once; it is not proof of document bytes. Navigation proof requires the current assessment, complete required controls, one exact locator, same origin, changed fingerprint and later recognized stage. These verifiers do not dispatch actions. A compromised renderer cannot turn assessment metadata into action authority; browser action admission, native confirmation, immutable document evidence, durable effect ownership and final submission remain independent backend/main-process gates.

Durable External-Effect Ledger `v0.63.0-alpha.1` closes the unjournaled pre-dispatch window for browser actions and AI completion/embedding provider calls. Response loss, unknown exceptions, local-evidence persistence failure and interrupted dispatch are consumed `UNCERTAIN` outcomes: AI fallback stops and browser automation requires user takeover. The ledger cannot prove remote state and does not authorize calendar UPDATE, unattended scheduling, portal submission or live-provider claims. Mail, calendar CREATE and Gemini cleanup retain their specialized journals. Source tests cannot establish actual provider retention, delivery, account-policy compliance or physical desktop behavior; every consumed uncertain attempt requires provider/browser reconciliation before a deliberately new action.

Durable Restore Rollback `v0.61.0-alpha.1` passed its full local source gate, exact backend-dist/delivered-package smokes, delivered supervisor lifecycle, source-controller-to-delivered-backend recovery protocol, protected pull-request integration and post-merge main checks. Schema-0029 source requalification covers 46 protected tables with v0.63; physical installed Windows recovery evidence remains separate. Path and lease checks are cooperative rather than handle-pinned isolation from a malicious local process; sequential writes are not a multi-file transaction or arbitrary power-loss guarantee. V2 forward admission preserves the explicitly compiled recorded-history graph, while rollback returns only the guarded operation's exact sealed targets. Neither can merge later history, automatically choose recovery, resume forward apply or prove remote state for an ambiguous effect. The delivered protocol gate mocks Electron key decryption and dialogs, so it does not establish real installed `safeStorage`, native-dialog, entry-point restart or power-loss behavior.

Alpha builds do not authorize live generic-portal submission. Production enablement requires named integration owners, current terms/legal review, authorized test accounts, real Windows desktop validation, portal replay plus supervised live validation, a protected signing certificate, incident-response ownership, and a rollback drill using the exact candidate installer. CAPTCHA solving and legal attestations are permanently human-only boundaries.
