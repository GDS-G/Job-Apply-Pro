# ADR-0066: Durable restore admission

## Status and purpose

Accepted for Durable Restore Admission `v0.56.0-alpha.1`. Exact-version local source and unsigned-package checks pass; protected integration is tracked in the readiness audit. ADR-0064 made desktop child ownership and restore observation explicit, but its recovery-required state disappeared with the desktop process. A forced termination could therefore reopen a workspace after incomplete multi-file replacement. ADR-0065 separately prevents a restored database from erasing recorded mail attempts. This decision adds persistent startup admission and authenticated completion evidence; it does not implement deterministic rollback, automatic resume or a multi-file atomic transaction.

## Workspace, ownership and early admission

`restore_admission.sqlite_database_path()` uses SQLAlchemy URL parsing, including driver-qualified SQLite URLs such as `sqlite+pysqlite`. File-URI/query overrides are rejected rather than guessed. `workspace_roots()` inspects both explicit `JAP_WORKSPACE_ROOT` and the configured database's parent. A different database override cannot silently hide a guard in the original explicit workspace. The desktop exports its managed data root as `JAP_WORKSPACE_ROOT`.

Normal startup checks each root through `assert_runtime_admission()` and holds `runtime_access()` for the API lifetime. Packaged migrate/serve, direct application creation, storage bootstrap and Alembic admission enforce the same gate before opening candidate storage. `workspace_access()` retains an OS-backed file handle: nonblocking byte locking on Windows and `flock` elsewhere. A process-local lease table tracks stream, ownership kind and nesting count; `_restore_owner` is a context-local owner token. Nested operations may reuse the exact owner's lock, but normal runtime cannot upgrade itself into a concurrent restore. PIDs and elapsed time do not prove stale ownership, and lock files are not deleted to force admission.

Restore requires one app-owned local workspace with the database directly beneath its root and disjoint document, backup, staging and restore-control directories beneath that root. `checked_path()` rejects unavailable/nonlocal drives, UNC paths, symlink/reparse aliases and paths outside the required root. `safe_relative()` rejects traversal, absolute/path-shaped input, reserved Windows names, alternate-data-stream syntax, control characters, ambiguous trailing dots/spaces and overlong paths. Inputs and existing targets must be regular, singly linked files. Unsupported external layouts require explicit review; the application does not relocate user data automatically. Cloud-synchronized workspaces are not validated by this release merely because a path appears local.

## Guard and encrypted records outside SQLite

`RestoreGateRepository` owns `restore-control/admission.lock`, `restore-control/active.guard` and `restore-control/operations/<operation-uuid>/`. Any existing, corrupt, unreadable or redirected active guard blocks normal startup; unreadable control paths also fail closed. The guard contains only an operation UUID, not profile information or credentials. `active_id()` reads a bounded canonical UUID and never treats a malformed marker as permission to continue.

`begin()` creates a fresh operation directory, writes authenticated encrypted `intent.enc`, flushes it, then writes and flushes `active.guard` before candidate files are replaced. `write_exclusive()` uses exclusive creation, file flush and `fsync`; records are never overwritten as retries. A crash before the guard is written has not started candidate-file replacement. A crash after it exists leaves admission blocked until authenticated completion can be proven.

`Intent` binds its version, canonical workspace, relative database/documents/staging paths, reviewed `RestorePlan`, authenticated `BackupManifest` and ordered `Target` inputs. Each target records path, SHA-256 and byte length. `Receipt` binds an intent hash and ordered final targets. Intent allows 4,096 inputs; the receipt allows 4,097 targets so a document-only restore at that input limit can also record its changed bookkeeping database. Record encryption uses the existing AES-GCM envelope and operation/kind-specific context `restore:v1:<uuid>:intent` or `restore:v1:<uuid>:receipt`. The encrypted intent's workspace is checked again during finalization. A key label is not a substitute for the actual original key.

## Closed-database preflight

`closed_restore_database_path()` and `assert_restore_source_closed()` require an existing regular, singly linked original database before any restore-specific database import, session or plan lookup. They reject linked parents/final components and call `assert_no_sqlite_sidecars()` using filesystem inspection only. Any `-wal`, `-shm` or `-journal` path blocks restore; unknown sidecars are not deleted or silently recovered as part of this operation.

Independent review reproduced a hot rollback journal being consumed merely by looking up an invalid restore plan. SQLite changed the database and removed the journal before the old apply-time check ran. The early guard now covers public CLI restore, the private owned entry and direct document-only restoration before repository reads. Missing databases no longer become empty database files through an unsuccessful restore lookup. Normal application startup may still perform ordinary SQLite journal recovery; that is distinct from an authorized offline replacement operation.

## Authenticated preparation and bounds

`RestoreRecoveryService.prepare()` requires a staged plan with canonical UUIDs, matching backup identity/categories, the owned archive filename and exact staging directory. `_authenticate_archive()` authenticates/decrypts the encrypted archive, verifies its SHA-256 and size, compares its internal manifest to the reviewed persisted manifest, and checks entry hashes/lengths. The review fingerprint is recomputed from plan/backup IDs, categories, archive hash and file count. Unknown, missing, extra, category-mismatched or case-colliding staged files are rejected.

`hash_file()` streams checks in 1 MiB blocks. `MAX_RESTORE_FILES` is 4,096, `MAX_FILE_BYTES` is 256 MiB, `MAX_RESTORE_BYTES` is 1 GiB expanded content, and `MAX_ARCHIVE_BYTES` is 384 MiB encrypted archive. Intent/receipt records and internal manifest metadata are limited to 4 MiB. These are supported-input limits, not a separate hard process-memory quota or arbitrary cancellation guarantee. The encrypted archive is authenticated in memory; compressed-entry inventory and expanded-size limits are checked before extraction reads.

Before creating intent/guard, `apply()` requires exclusive restore ownership, clear admission, a closed current database, and a bounded current-file hash. Database replacement also calls `BackupService._require_resolved_media_cleanup()` and `_require_preserved_mail_attempts(current_database, staged_database)`. A filesystem-only closed-database check of the staged database immediately precedes the mail-history read, preventing acceptance of history present only in a staged sidecar that replacement would omit. The mail guard preserves exact send audits and claims under ADR-0065. Neither a filesystem marker nor a newer backup schema replaces external-effect history preservation.

## Replacement, bookkeeping and completion

After admission begins, a database replacement writes a fresh encrypted `database-preimage.enc` under the operation directory, using context `restore:v1:<uuid>:database-preimage`. It does not overwrite an existing `.pre-restore` file or older recovery copy. This preimage is preserved evidence, not an implemented automatic rollback procedure; document preimages and a complete rollback transaction are not provided.

`_replace()` rechecks input/target ownership, streams to a unique adjacent exclusive temporary file, bounds actual length and verifies the reviewed hash, flushes the completed temporary file, then replaces the individual target. An interrupted or rejected operation preserves its guard and diagnostic/recovery files. Document restore overlays only selected entries and leaves unrelated documents alone. Individual replacement is not atomic across the entire set of files.

`OperationsRepository.save_restore_result()` persists the recovered backup manifest and applied restore plan in one database transaction. The owned CLI closes/disposes SQLite handles before replacement and after this bookkeeping. Final target hashes are then recorded; the committed database is included even for document-only restoration because its bookkeeping changes that database. Unexpected SQLite sidecars at completion prevent finalization.

`finalize()` acquires exclusive ownership, requires the active operation ID, authenticates both records, recomputes the intent binding, requires the exact ordered target inventory, rechecks restored document bytes against the reviewed inputs, and hashes every recorded target. Only then may `finish_verified()` remove the guard. A missing/corrupt receipt, wrong/missing key, changed target, different workspace or unknown sidecar leaves the guard intact. Finalization does not open or migrate SQLite and is not an unconditional clear operation.

## Entry points and visible recovery

`restore-status` is database-free and key-free. It reports whether recovery is required, emits safe JSON when a console stream is available, and exits with code 3 when blocked. `restore-finalize --operation-id <uuid>` verifies an already completed operation using the original key and target evidence; it cannot resume writes, invent a receipt, remove an arbitrary marker or roll back files. The windowed backend may not have stdout; the desktop supplies visible recovery guidance independently.

Database replacement is available only through the dedicated offline CLI under exclusive ownership. The legacy `BackupService.apply_staged_files()` write entry is disabled so it cannot bypass admission. Document-only `apply_offline()` uses the same guarded protocol and is unavailable while another normal runtime owns the workspace.

Desktop startup checks durable admission before key creation, backend work and updates. A native recovery dialog explains preservation and the app exits cleanly. A missing key is not regenerated when an existing database or restore history proves prior workspace use. Existing valid keys continue to load, and genuinely fresh installations can initialize normally. Supervisor checks also block start and update preparation when durable recovery is required; ADR-0064's non-killing restore observation remains in force.

## Packaged verification ownership

`scripts/test_packaged_backend.ps1` uses `Initialize-SmokeLifecycle()` to track separately captured API backends, workers and offline commands. `Start-SmokeBackend()` retains and pins the exact `Start-Process` object before readiness observation, including a startup failure before the caller assignment completes. Only a previously owned and pinned API backend is eligible for cleanup termination; accepting a kill request is not exit proof.

`Get-SmokeWorker()` treats a CIM process record as a candidate, not ownership. It pins a handle and verifies the actual executable, microsecond-normalized creation time and captured parent's lifetime before adding that object to the owned list. This closes the discovery-to-handle PID-reuse race. Rejected or zero/null handles never authorize a wait or kill. A worker timeout preserves evidence and fails; the helper never force-kills workers.

`Invoke-SmokeCommand()` retains migration/restore handles before `Wait-SmokeCommand()` performs bounded observation. A timeout or failed handle capture preserves the synthetic workspace; migration and restore writers are never terminated to meet a test deadline. `Stop-SmokeBackend()` and `Complete-SmokeCleanup()` keep failure preservation sticky, continue checking other captured children after one failure, and remove only the validated newly created synthetic workspace after all required exit evidence succeeds. Any functional verification failure also preserves artifacts. These helper checks do not promise arbitrary descendant containment or preservation after an external CI runner is destroyed.

## Validation and explicit limits

Tests cover cooperative cross-process admission, interruption at persistence barriers, authenticated receipt finalization, missing/wrong keys, authenticated-record failures and changed targets, unsupported layouts, real Windows junctions, hard links, missing files, reserved/ambiguous paths, hot journals before plan lookup, database-only/document-only/combined restore, single-transaction bookkeeping, mail-history preservation and visible desktop/key gates. Both packaged copies verify fresh encrypted database preimage and receipt, no active guard after successful completion, and retained mail outcomes. The helper explicitly creates owned fixture directories and passes embedded Python through stdin to avoid Windows PowerShell native-argument quote rewriting. Exact counts, initial helper failures and artifact evidence are in the readiness audit.

The guarantees apply to cooperating processes and checked supported local layouts. Repeated pathname checks are not handle-pinned containment against a noncooperating same-user attacker racing files. Windows file `fsync` uses `_commit`; this code does not promise arbitrary hardware power-loss survival or Windows directory-fsync semantics. Full process-tree containment, deterministic rollback/resume, arbitrary external/cloud workspace layouts and physical crash/storage-pressure acceptance remain separate work. Do not delete recovery records or generate a replacement key to force startup.
