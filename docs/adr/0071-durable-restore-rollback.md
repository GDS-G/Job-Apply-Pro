# ADR-0071: Durable restore rollback

> ADR-0082 extends this compatible v2 record format with a separately fingerprinted, immutable-direction `RESUME` decision. The rollback behavior and all historical guarantees below remain in force.

## Status and scope

Accepted as the source design for Durable Restore Rollback `v0.61.0-alpha.1`. The integrated candidate adds authenticated, explicit rollback for an interrupted local offline restore and an isolated native packaged recovery path. Its full source gate, exact backend-dist and installer-payload smokes, delivered supervisor, and source-controller-to-delivered-backend recovery protocol are recorded below. It remains alpha until protected CI/security and physical installed Windows recovery validation are recorded. It does not make multi-file replacement atomic, automatically choose rollback, resume an unfinished forward apply, merge later history, repair arbitrary files, or promise survival of every hardware/power-loss condition. A completed restore with an authenticated `APPLIED` receipt may only be finalized; it cannot be rolled back through this protocol.

The v2 protocol retains the v1 completion reader for already-existing recovery evidence. A v1 operation did not preserve every document before-image, so it remains verified-completion or manual-recovery only. No migration rewrites or upgrades old recovery directories.

## Protocol records and bounds

`services/restore_rollback.py` defines the frozen, extra-forbidden recovery models. `POLICY = interrupted-restore-rollback/2` versions the contract.

- `Image`: deterministic encrypted object name, plaintext SHA-256 and plaintext size. Names are `sha256(relative target path).before.enc` or `.after.enc`.
- `Replacement`: one workspace-relative target with an optional `before` image and required `after` image. A missing before image means the operation introduced that exact file.
- `PreparedRestore`: version, policy, canonical operation/workspace identity, the source v1 `Intent`, applied `RestorePlan`, and the complete ordered replacement list.
- `RollbackDecision`: the prepared-intent digest, operator-visible review fingerprint and fixed `ROLLBACK` action.
- `TerminalReceipt`: prepared-intent digest, terminal outcome (`APPLIED` or `ROLLED_BACK`) and the exact ordered terminal path/hash/size inventory. A null hash/size is an authenticated absent target after rollback.

`MAX_RESTORE_FILES` remains 4,096 source inputs; the database bookkeeping target makes at most 4,097 replacements. Each plaintext file is at most 256 MiB. Staged postimages, retained preimages and each terminal side are independently bounded to 1 GiB. Each encrypted object is bounded to 512 MiB plus 4 KiB envelope allowance, and every control record is bounded to 4 MiB. The gate rechecks record capacity for every publication attempt, including retained pending siblings. All record models reject extra fields, malformed hashes, noncanonical operation IDs and unsupported relative paths.

The gate stores immutable `intent.v2.enc`, optional `decision.v2.enc`, `receipt.v2.enc`, and encrypted objects below `restore-control/operations/{operation_id}`. AES-GCM contexts bind each control record to version, operation and kind, and each object to operation and deterministic object name. V2 publication uses exclusive pending files, fsync, an owning restore lease and a final rename. Incomplete pending siblings remain evidence but cannot activate or replace a published object. Hard links, reparse points, redirected paths, wrong keys, wrong contexts, oversize content and corrupt present records fail closed.

Recovery evidence also has a global admission quota. The inventory permits at most 128 retained operation directories and 8 GiB total, while reserving 5 GiB of headroom before admitting a new operation. An operation permits at most `2 * 4,097 + 10` files. Its current size plus any new publication must remain within the 5 GiB per-new-operation reservation as well as the global retained limit. Unknown, noncanonical, linked, redirected, oversize or otherwise non-regular inventory fails closed rather than being skipped.

## Preparation and forward apply

`RestoreRollback.apply(source)` requires the exclusive restore lease, a clear gate, exact workspace binding and a cleanly closed original database. `RestoreRecoveryService.prepare()` must first reconstruct the complete reviewed source intent; changed archive, staging, plan, manifest or target bytes are rejected before the staged SQLite database is queried. For database restores, the staged database must also be cleanly closed. The narrow unresolved-media and mail-attempt guards remain defense in depth.

The broad forward-history guard is explicit schema policy, not schema reflection and not a pre-call intent journal. It recognizes 43 compiled schema-0027 tables. Query-only inspection requires exact physical table, column, index, uniqueness and foreign-key forms; one supported Alembic revision; no triggers, views, virtual tables or unknown non-operational tables; and only compiled enum/value shapes. Each table is limited to 10,000 rows, the snapshot to 100,000 rows and 128 MiB of materialized values, each cell to 8 MiB, JSON to 50,000 nodes/32 levels, and inspection to ten seconds. Unsupported or legacy-with-history schemas fail closed.

If either snapshot has protected history, every current row across the application, evidence/document, workflow, portal/browser/challenge, OAuth, communication/calendar, AI/model/media and readiness graph must exist unchanged in the candidate with valid relational and ownership closure. Mutable OAuth credentials/sessions, communication configuration, browser/portal/supervised/challenge sessions, provider sync/calendar snapshots and AI cache must be exact sets so a restored-only row cannot revive revoked authority or stale state. Encrypted fields are authenticated with their fixed record contexts. Candidate immutable document history is limited to 1,000 versions, 72,000,000 bytes per encrypted file, 256 MiB cumulatively and 30 seconds; current and staged document bytes are decrypted and checked against recorded SHA-256 values. This preserves durably recorded history and its dependencies. It cannot prove an external side effect that occurred before any durable local intent or outcome record.

One bounded read of the closed original database becomes the immutable comparison snapshot and the database rollback preimage. The broad guard compares that exact byte snapshot with the authenticated staged candidate before bookkeeping. After bookkeeping, it inspects the serialized result in memory and compares it to the same original snapshot again. Immediately before guard activation, the service rechecks every live target against the sealed `BEFORE` images; an independently changed file fails admission.

Every staged input is stream-hashed and the aggregate postimage size is checked before operation allocation. The candidate database is deserialized into a private `:memory:` SQLite connection with extensions disabled, `trusted_schema=OFF` and foreign-key enforcement enabled. The two bookkeeping tables must match their exact SQL text, columns, primary/index shapes and `restore_plans.backup_id` foreign key, and the database may contain no main/temp trigger or view. A default-deny SQLite authorizer then permits only enumerated direct reads, transaction actions, required inserts and named-column updates to `backup_manifests` and `restore_plans`. A non-null recursive source, delete, function, pragma, attach, schema change, unrelated table or future unknown action is denied. The final serialized bytes are rechecked for mail-attempt preservation, broad recorded-history preservation and size without ever creating a plaintext scratch database. The service then:

1. Allocates a unique operation and private objects directory without activating the runtime guard, but only after the global evidence quota admits it.
2. Reads and seals the original closed database even for a documents-only restore, then releases those plaintext bytes; the mandatory collective preflight authenticates every retained image before guard publication.
3. Captures each existing document before-image and intended staged after-image sequentially, releasing each plaintext value before reading the next. The prepared in-memory database after-image is sealed last and its plaintext buffer is then released.
4. Validates the complete target/path/image inventory and authenticates every retained image and every live `BEFORE` state before the guard or first live-target write.
5. Publishes the encrypted prepared intent, activates `active.guard`, installs document targets in sealed order and installs the database last.
6. Rechecks all live `AFTER` states, publishes an `APPLIED` receipt, reauthenticates receipt/intent/targets and only then clears the guard.

Any preparation failure before guard activation attempts to remove only that operation's strictly inventoried, never-active evidence while the exclusive lease is still held. It never purges historical recovery evidence. If safe cleanup cannot be proved, the residue is retained and counted by later quota admission; cleanup failure does not hide the original preparation error.

This order prevents SQLite bookkeeping from mutating the original database before rollback evidence exists. It is still sequential multi-file replacement: a crash after guard activation intentionally leaves startup and updates blocked.

## Inspection, rollback and finalization

`RestoreRollback.inspect(operation_id)` authenticates the prepared record, all encrypted images, current live target states and any decision or receipt. An active receipt-free v2 operation reports `INTERRUPTED` or `ROLLING_BACK` and exposes a review fingerprint computed as SHA-256 over the policy, fixed rollback action and canonical prepared-intent digest. It does not change targets.

`RestoreRollback.rollback(operation_id, review_fingerprint)` accepts only the still-active original operation and exact current review fingerprint. Before the first rollback write it authenticates every before/after image and proves every live target is exactly its known `BEFORE` or `AFTER` state. Unknown, missing, linked or externally changed content blocks the whole rollback.

The service durably publishes the authenticated rollback decision before changing targets. Repeated recovery skips targets already at `BEFORE`, restores existing preimages, and removes only an introduced file still matching its authenticated after-image. The database remains last. It then verifies all `BEFORE` states, writes a `ROLLED_BACK` receipt, verifies it again and clears the guard. An interrupted rollback can therefore converge without replaying completed target writes.

`RestoreRollback.finalize(operation_id)` never invents completion. It requires the active operation, authenticated terminal receipt and exact matching live terminal state. An `APPLIED` receipt cannot coexist with a rollback decision; a `ROLLED_BACK` receipt requires it. Clearing or changing the guard prevents later rollback from reverting newer local history.

## CLI and application boundaries

`desktop_entry.py` adds database-free recovery commands that use the original `EnvironmentKeyProvider` and require exactly one resolved workspace:

- `restore-status` remains key-free and reports whether admission is blocked.
- `restore-inspect --operation-id <uuid>` prints only the authenticated bounded inspection result.
- `restore-rollback --operation-id <uuid> --fingerprint <sha256>` performs the explicit reviewed rollback.
- `restore-finalize --operation-id <uuid>` only clears verified terminal completion.

Argument combinations are strict. Recovery commands do not create a replacement key, open the application database before admission, guess an operation, retry automatically or expose decrypted evidence. Missing/wrong keys, invalid IDs, missing guards and malformed records fail without reporting success.

Packaged startup resolves the installed resources and app-owned user-data database rather than accepting `JAP_PROJECT_ROOT` or `JAP_DATABASE_URL` overrides. If an active guard is present, Electron enters a terminal recovery-only session before creating a key, running migrations, starting the API, constructing renderer services or checking for updates. The main process loads only the existing OS-protected master key through Electron `safeStorage`; it never creates a replacement recovery key and never exposes the plaintext key or recovery decision to the renderer.

The native controller launches the bundled console backend with redirected hidden pipes and a recovery-only environment, authenticates the exact guarded operation, accepts only the fixed bounded JSON inspection shape, rejects any stderr, limits stdout/stderr, and fails closed after a 60-second command deadline. Its warning dialog defaults Cancel to **Keep workspace blocked**. An interrupted or already-rolling-back operation may proceed only through **Roll back exact restore** with the inspected fingerprint. An authenticated terminal `APPLIED` or `ROLLED_BACK` receipt may proceed only through **Finalize exact restore state**. On the expected success path, the controller reinspects the exact terminal state and requires the guard to be clear. Cancellation and failures before a mutating command leave the guard in place. Any ambiguous result after an authorized backend mutation closes the recovery-only app without starting normal services, but the backend may already have reached a verified terminal state and cleared the guard; preserve all evidence and reauthenticate on-disk state before another action. Missing/corrupt keys, legacy v1 evidence, unexpected output, helper failure and all ambiguous states remain manual-review cases rather than inferred success.

## Package verification and validation

The exact packaged restore verifier is deliberately independent of application models and opens no SQLite database. Without printing paths, keys, hashes or plaintext, it requires exact intent/receipt/source keys; exact v1-source/v2-recovery versions, policy, statuses and category relationships; canonical operation and workspace binding; reviewed-to-applied plan equality except `status`/`applied_at`; and the prepared-intent digest. It maps the ordered, case-unique source inputs to exact document targets with the database last; checks 4,096-input/4,097-target, file and aggregate bounds; enforces deterministic unique object names; authenticates every before/after object sequentially; proves original database and existing-document preimages; binds each document after-image to its source hash/size; and compares the exact `APPLIED` receipt with streaming live-target hashes. The operation root must contain only `intent.v2.enc`, `receipt.v2.enc` and `objects`, and the object directory must equal the referenced set, so an active guard, rollback decision, pending/unknown/plaintext file, extra record or unreferenced object fails verification. Legacy v1 finalization remains a separate source boundary.
