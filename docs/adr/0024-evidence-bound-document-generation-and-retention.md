# ADR-0024: Evidence-bound document generation and retention

- Status: Accepted
- Date: 2026-08-11
- Build: Document Generation & Retention `v0.15.0-alpha.1`

## Context

The candidate knowledge system can import documents, propose claims, and lock user-reviewed facts, while applications and portal workflows choose a document version. The product requirements also call for tailored resume and cover-letter variants and a durable record of the exact file sent to an employer. Generating prose without evidence controls could invent qualifications, and recording only a logical document would not prove which immutable version a portal displayed and accepted.

## Decision

Tailored generation is a two-step preview and approval workflow. A preview may select only unsuperseded, locked, verified claims whose permitted use is `APPLICATIONS` or `ANY`. Deterministic meaningful-token overlap ranks those claims against the job title, employer, and persisted requirements. The preview contains the exact sections, evidence claim IDs, matched requirement IDs, unresolved required requirement text, and a SHA-256 review fingerprint.

Generation recomputes the preview and requires both the unchanged fingerprint and the fixed `APPROVE TAILORED DOCUMENT` phrase. It renders DOCX or PDF from the reviewed sections, encrypts the bytes and extracted layout under the document-version context, persists the generated document/version/evidence source, and commits a generation audit in the same repository transaction. Generated content does not propose new candidate claims because its authority derives from existing reviewed evidence.

The renderer displays every preview paragraph but never receives generated bytes. After the owner approves generation, Electron main may fetch the immutable version through the authenticated loopback content endpoint and write it only to a destination selected through the native save dialog. Canceling export does not discard the encrypted retained version.

Submitted-document retention is version-specific. It verifies the application profile, immutable version SHA-256, and exact portal-displayed filename before recording the role and an upload fingerprint. The standalone retention API requires `RETAIN SUBMITTED DOCUMENT`. A portal adapter may record the same evidence after its own stronger fingerprint-bound submission approval and identifier-backed confirmation. Identical application/version/role/upload captures are idempotent.

## Consequences

- A generated qualification is traceable to reviewed candidate evidence and cannot silently change between preview and approval.
- Missing required qualifications remain visible instead of being fabricated or hidden.
- Generated originals and extracted text remain encrypted; audits store identifiers and fingerprints rather than candidate prose.
- Decrypted export is an explicit owner action contained in Electron main; the sandboxed renderer receives metadata only.
- Confirmed applications retain the exact submitted version, filename, digest, role, and portal-run-derived upload fingerprint.
- Deterministic overlap is intentionally conservative and less stylistically sophisticated than model-generated tailoring. Richer ranking or writing may be added only behind the governed AI boundary while retaining the same evidence and approval invariants.
- Legacy binary DOC conversion, OCR, and advanced template/layout fidelity remain separate source work.
