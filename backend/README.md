# Job Apply Pro backend

The backend is a loopback-only FastAPI service that owns validated business logic, workflow state, and persistence. Install it from the repository root with:

```powershell
python -m pip install -e ".\backend[dev]"
python -m alembic -c backend\alembic.ini upgrade head
```

The backend exposes health, runtime status, workflow controls, event history, candidate, job, application, encrypted backup and restore staging, resumable checkpoints, browser sessions, bounded layout-aware candidate-document conversion and OCR, candidate knowledge, versioned reviewed answers, typed application-scoped question provenance and review-gated drafting, reviewed portal-field binding previews and approvals, explainable immutable resume selection, evidence-ranked tailored documents, submitted-document retention, governed AI with independent OpenAI-compatible, native Gemini, and llama.cpp adapters, expanded portal replay coverage, supervised portal execution, challenge, validated/encrypted provider registration control, OAuth/PKCE provider connection, encrypted incremental mail synchronization, encrypted bounded calendar snapshots, account-bound CREATE-only calendar plans and durable one-attempt claims, communication, follow-up, mutation audits, operational reporting, signed-license state, redacted support diagnostics, and help endpoints under `/api/v1`. Electron receives sanitized synchronization status and derives privacy-safe in-app and native notifications from authenticated local records; the backend exposes neither provider cursors nor calendar details through sync status and adds no unauthenticated surface. The packaged executable also owns migration, loopback serving, and offline restore commands.

Runtime storage admission checks both the explicit workspace and configured database parent before opening SQLite. Offline restore requires exclusive ownership and a closed existing database, authenticates the complete reviewed archive/staged-source identity before querying a staged SQLite file, and blocks unresolved media. The schema-0028 forward-history guard validates 44 compiled table definitions plus indexes, uniqueness, foreign keys, encrypted fields, relational ownership and immutable document bytes; every current protected row—including exact calendar claim → audit → plan relationships—must survive unchanged, and mutable authority/session/cache tables must remain exact sets. One exact original-database byte snapshot is both the comparison baseline and rollback preimage. The final serialized bookkeeping bytes are checked against that same snapshot, and every live target must still equal its sealed `BEFORE` state immediately before guard activation.

Calendar Attempt Admission `v0.62.0-alpha.1` stores immutable CREATE-only plans with exact provider/account/connection and policy bindings. Every event is private and busy with provider-default reminders, attendees, invitations and conferencing disabled. A transaction inserts the `PLANNED` audit and unique per-plan claim before token lookup or transport. Exact-key replay is relationship-checked; different keys, recovered `PLANNED` attempts and ambiguous outcomes never redispatch. Google receives a deterministic provider-valid event ID and Microsoft Graph a deterministic UUID transaction ID, but those duplicate defenses do not authorize blind retry. Recurrence, UPDATE and unattended writes remain disabled. See [ADR-0072](../docs/adr/0072-calendar-attempt-admission.md).

V2 restore prepares bookkeeping in a deserialized `:memory:` SQLite database under exact physical schemas and a default-deny authorizer. Only direct reads, transactions, required inserts and named-column updates in `backup_manifests` and `restore_plans` are allowed; triggers/views, recursive sources, deletes, functions, pragmas, attaches, schema changes, unrelated tables and unknown SQLite actions are denied. It stream-checks aggregate staged input before operation allocation, admits retained evidence under per-record, per-object, per-operation and global count/size quotas, and seals database/document plaintext sequentially before activating the guard. A pre-guard failure discards only the newly allocated, strictly inventoried operation when safe cleanup can be proved; uncertain residue remains retained and counts against later admission. The database installs last and an authenticated terminal receipt is required. `restore-status` stays key-free; `restore-inspect` returns the bounded authenticated state; `restore-rollback` requires the exact review fingerprint; `restore-finalize` clears only verified terminal evidence. The packaged Electron main process mediates these commands through the existing `safeStorage` key, a bounded hidden console child and a cancel-default native dialog while normal application services remain off. Legacy v1 operations remain completion/manual-recovery only. Exact schema-0028 backend-dist and installer-payload smokes plus delivered supervisor/recovery-protocol gates pass for `v0.62.0-alpha.1`. The v0.63 source policy advances to schema 0029 and validates 46 protected tables, including exact external-effect replay authority, while empty 0025–0028 compatibility remains fail-closed. Protected CI/security, a v0.63 package candidate and physical installed-app/key-store/dialog recovery remain separate. Automatic forward-apply resume/choice also remains separate work. See [ADR-0066](../docs/adr/0066-durable-restore-admission.md), [ADR-0071](../docs/adr/0071-durable-restore-rollback.md), and [ADR-0073](../docs/adr/0073-durable-external-effect-ledger.md).

Public Greenhouse discovery is available under authenticated `/api/v1/discovery/greenhouse/list`, `/review` and `/import`. Only fixed-origin public GET requests reach the provider. Import rechecks the reviewed source fingerprint, then atomically saves immutable source data and a profile-bound `DEDUPLICATED` application. Qualification remains `NOT_EVALUATED`; no browser, candidate transmission or submission occurs. Real jobs cannot use mock controls or caller-fabricated generic transition events. See [ADR-0068](../docs/adr/0068-greenhouse-public-discovery.md).

Source-bound mail distinguishes explicit `NEW_MESSAGE` from `REPLY`. Replies bind verified synchronized source, stable OAuth identity and current connection; legacy/local analysis cannot grant that authority. Gmail preserves exact threading headers; Outlook uses immutable source IDs and a single reply request. Offline new-message previews remain unsendable, including after account connection or restore. See [ADR-0069](../docs/adr/0069-source-bound-replies.md) for contracts, storage migration, limits and acceptance gaps.

Reviewed Greenhouse readiness is available under `/api/v1/applications/{application_id}/job-review`, with requirements/qualification/resume preview and approval endpoints. Exact source lines, locked same-profile evidence and immutable document fingerprints govern append-only encrypted reviews and atomic milestones. Generic resume selection cannot bypass this review. This deterministic service does not construct an AI registry or contact providers. See [ADR-0070](../docs/adr/0070-reviewed-job-readiness.md).

Browser sessions are available under `/api/v1/browser`. Session creation, observation, verified actions, action history, takeover, return, restart, and stop all use the same privileged API authentication. Production automation is locked by default, so only loopback fixture URLs are accepted.

Candidate knowledge is available under `/api/v1/knowledge`. The backend validates and extracts PDF, DOCX, RTF, TXT, and Markdown imports, encrypts originals and extracted layouts, proposes evidence-linked claims, requires explicit review before locking facts, merges overlapping experience periods, records answer provenance, and retrieves only permitted locked knowledge. PDF layout lines can retain page/row/column coordinates with conservative column-major ordering; DOCX paragraphs and tables remain in top-level document order with table/row coordinates. Tailored previews and generation use only locked verified claims approved for application use, bind approval to the exact evidence/requirement fingerprint, render DOCX or PDF, encrypt the result, and persist a generation audit. Authenticated version-content retrieval exists for Electron-main native export; the renderer never receives decrypted bytes. Submitted-document evidence retains the exact version, filename, digest, role, and upload fingerprint only after upload verification and explicit confirmation. Retrieval retains its offline keyed baseline; semantic embeddings and reranking are available only through the governed AI Gateway boundary.

AI operations are available under `/api/v1/ai`. The gateway owns provider configuration, model capabilities, routing policy, prompt/schema versions, privacy checks, redaction, retries, fallback, cost limits, encrypted caching, invocation metadata, embeddings, reranking, bounded tools, six initial agents, and evaluations. OpenAI-compatible cloud, secondary compatible, and loopback llama.cpp servers share the same internal contract. With no `JAP_AI_CONFIG_JSON`, status is `not_configured` and no provider call is possible.

Gemini `complete()` uses one invocation-local work budget across uploads, processing-state waits/GETs and inference. The original resource is registered before secondary metadata validation, polled through the fixed Files endpoint and retained as the only cleanup target. Thirty shared processing GETs and a separate 30-second cleanup network allowance are product limits, not provider guarantees or hard transport cancellation. See [ADR-0067](../docs/adr/0067-gemini-processing-budget.md) for constants, functions, error precedence and exact trust boundaries.

Reference ATS operations are available under `/api/v1/portals`. A run discovers and validates a fixture job, deduplicates it, persists requirements and fit evidence, chooses an approved resume, maps and completes the multi-page form, verifies the upload, and stops at `READY_TO_SUBMIT`. Confirmation requires the exact review fingerprint and fixed approval phrase; the adapter records `SUBMISSION_CONFIRMED` only after a strong confirmation-page signal, then retains the exact submitted version as application evidence. The adapter rejects every non-loopback origin.

Challenge operations are available under `/api/v1/challenges`. Sessions persist detection evidence, typed questions, verified answers, timers, review fingerprints, recovery events, and CAPTCHA intervention state. Answer suggestions are deterministic and limited to encrypted contact facts or locked approved application answers. Model-route responses describe the capability tier for the governed AI Gateway; challenge code never calls a provider directly.

The portal catalog under `/api/v1/portals/catalog` declares generic-agent workflows for all Phase 9 targets. `/identify` matches sanitized page evidence against domain and signal fingerprints, while `/replays/validate` reports per-portal accuracy. Every catalog entry has `production_enabled=false`.

Supervised runs under `/api/v1/portals/supervised` can open a visible persistent browser for an explicitly allowlisted catalog portal. Start, capture, submit, and stop operations persist exact page fingerprints and append-only evidence. Login, MFA, CAPTCHA, assessments, legal attestations, and signatures remain manual. Final submission requires a separate capability gate, the current review fingerprint, one unambiguous submit control, and the fixed approval phrase; a confirmation identifier is required before recording `SUBMISSION_CONFIRMED`. If the exact reviewed Greenhouse submit click loses its worker response, the separately reviewed submission-reconciliation route performs two fresh same-origin, changed-page, catalog-backed, identifier-bearing read-only proofs without replay. It keeps the original operation/attempt `UNCERTAIN`, exposes only a keyed identifier fingerprint, and relies on the existing current-page supervised capture to confirm and stop the run while that page remains current.

Communication operations are under `/api/v1/communications`. Gmail and Outlook payloads normalize to a shared message model before deterministic classification, correlation, and reply drafting. Protected analysis and draft payloads are AES-256-GCM ciphertext; searchable rows retain only provider identifiers, category, review state, timestamps, and workflow linkage. Calendar plans preserve proposed and prior event snapshots, while every send/create/update attempt uses a fingerprint, idempotency key, actor, status, and provider resource identifier. All live adapters remain unconfigured unless an OS-protected credential reference is explicitly authorized.

Verified Mail Attachments adds immutable ordered PDF/DOCX manifests, workflow/profile ownership checks, bounded encrypted reads and supported-container validation. Reviewed bytes and the provider connection are checked again before dispatch. A database claim prevents a second attempt for the same draft, including uncertain outcomes; provider acceptance is not recipient delivery. Outlook now sends through one `Mail.Send`-compatible request. See [ADR-0065](../docs/adr/0065-verified-mail-attachments.md) for exact limits, failure states and recovery protections. Run backend checks from the repository root with `pnpm backend:typecheck`; it explicitly loads the strict backend configuration and checks both packaged probe helpers.

Provider configuration validation/import/clear operations are authenticated and accept at most 64 KiB. Imports require at least one provider or OAuth client and reject unknown fields, including passwords, tokens, and client secrets. Imported registration metadata is encrypted as one authenticated configuration envelope. Process-level `JAP_COMMUNICATION_CONFIG_JSON` has precedence and makes the desktop configuration read-only. API responses expose only source, providers, requested scopes, read/write flags, categories, and update time; client IDs and raw JSON are never returned.

Candidate, checkpoint, and candidate-knowledge routes require `JAP_MASTER_KEY`, a base64-encoded 32-byte local key. When `JAP_API_TOKEN` is configured, all `/api/v1` routes except health require the `X-Job-Apply-Pro-Token` header. The API never persists or returns either secret. OpenAPI documentation is available at `http://127.0.0.1:8765/api/docs` while the service is running.
